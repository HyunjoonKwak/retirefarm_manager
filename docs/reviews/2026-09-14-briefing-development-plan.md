### 기존 JSON 호환

확인한 첨부는 `schemaVersion: 1`, `observationWindow`, `sources`, `method`, `gradeOrder`, `jujube/round.packageKg`, `rows`, `smartstore`, `correction`, `limits` 구조다. 새 통합 계약과 직접 호환되지 않는다.

- 전용 `work-observations-v1` 어댑터로 미리보기 후 가져온다. 원본 파일·해시·수신시각·원문 버전은 별도 보존한다.
- `[날짜, 특, 상, 중, 하]` 행은 `gradeOrder`와 길이를 검증한다. 관측값의 출처는 공개 일별 평균이며 경매 원거래로 승격하지 않는다.
- `observationWindow`의 시간 정밀도를 보존한다. 수신시각을 실제 관측시각으로 대입하지 않는다.
- `smartstore.observations=[]`와 `panelEstablished=false`를 그대로 유지한다. 알 수 없는 금액은 null과 사유로 기록한다.
- Markdown 보고서는 원문 보관용으로 가져오며 본문의 표를 자동으로 통계 원장으로 만들지 않는다.

## 5. 품종별로 흩어진 가격을 의미 있는 정보로 만드는 방법

### 비교 단위를 먼저 고정

원거래의 법인·품목·품종·산지·등급·포장 중량·단위를 보존한다. 표기 별칭은 검증된 매핑 테이블과 버전으로 관리하고, 미확정 품종은 별도 그룹에 둔다. kg 환산이 불가능한 거래를 가격 분포에 억지로 섞지 않는다.

주요 지표는 거래금액/중량의 kg당 가중평균, 동일 포장 단위의 수량 가중평균, 중앙값·사분위 범위, 거래량·거래 수·거래일 수다. 원자료에서 가격과 수량의 단위를 먼저 확인한다. 소표본과 혼합 등급에는 신뢰도 설명을 붙이고 이상치는 원본을 삭제하지 않고 표시·필터한다. 분위수의 가중 여부와 산식을 `statisticsVersion`으로 고정한다.

전주 비교는 같은 조건의 표본으로 계산한다. 전체 평균 상승이 고가 품종의 비중 증가 때문인지 동일 품종의 가격 상승 때문인지 구분해 보여준다. 거래량 합계와 품종 구성비를 나란히 제공한다.

### 산지 선택 UI

- 현재 기간·법인·품목 조건에서 실제 관측된 산지×품종 집계로 선택 가능 상태를 만든다.
- 관측됨: 거래 건수·최신 거래일과 함께 강조. 해당 조건에서 0건: 비활성화하고 이유 표시. 수집 미완료: ‘확인 중’으로 표시한다.
- 과거에는 관측됐지만 현재 기간 0건이면 ‘최근 거래 없음’으로 표시하고 기간 확장 동작을 제공한다.
- 산지 변경으로 기존 품종 선택이 유효하지 않으면 해제 사실을 알린다. 키보드·스크린리더에서도 상태와 사유를 알 수 있게 한다.
- 이 상태는 **수집된 시장 거래에서 검색 가능함**을 뜻한다. 실제 산지의 생산·출하 여부 전체를 보증하는 문구는 쓰지 않는다.
- 구현은 원거래 목록을 내려받는 대신 DB groupBy/집계 API와 조건별 캐시를 사용한다.

## 6. 네이버 쇼핑검색 연동 준비

### store_manager에서 확인한 사실

- `src/lib/naver/api-hub.ts`: 인증 사용자→현재 store→`stores.api_config` 조회, 서버에서 비밀값 복호화, 15초 제한·캐시 비활성 요청 구조.
- `src/app/api/trends/research/route.ts`: `/search-trend/v1/search`, `/shopping/v1/category/keywords`, `/shopping/v1/category/keyword/device`를 호출한다. 상품 가격 검색 구현은 아니다.
- `naverApiHubClientId/Secret`은 Naver Cloud API Hub 헤더를 사용한다. 별도의 `naverClientId/Secret`은 커머스 연동용이다. 확인한 설정 파일의 변수명에는 쇼핑검색 전용 키가 없었다. DB에 저장된 자격증명의 쇼핑검색 권한은 아직 검증하지 않았다.
- 다른 프로젝트의 비밀값을 출력하거나 복사하지 않았다. **권한이 없다고 단정하지 않으며**, 기존 앱의 안전한 설정 경로에서 API 종류·허용 범위를 확인하는 연결 작업을 남긴다.

공식 상품 검색은 `GET https://openapi.naver.com/v1/search/shop.json`, `X-Naver-Client-Id/Secret` 인증이다. 제목·링크·최저가·몰명·상품 ID 등을 제공하지만 옵션별 가격과 배송비 확인을 대신하지 않는다. API 정렬을 소비자 화면의 비광고 순위로 간주하지 않는다. [네이버 공식 문서](https://developers.naver.com/docs/serviceapi/search/shopping/shopping.md)

### 수집·가공 흐름

1. 서버 전용 `naver-shopping-search.ts` 어댑터와 공급자별 자격증명 resolver 분리. API Hub 키를 다른 호스트에 시험 전송하지 않는다.
2. 쿼리·정렬·페이지·관측시각·응답 상태와 검색 순서를 `SearchSnapshot`에 저장. 제목의 HTML은 텍스트로 정리한다.
3. 검색 결과에서 판매처 후보를 추린다. 몰 이름만으로 동일 판매처를 확정하거나 쇼핑 상품 ID를 스마트스토어 옵션 ID로 취급하지 않는다.
4. 대추방울·원형 방울, 실제 중량, 혼합/주스용/가공품을 분류하고 불확실한 결과는 검토 대기한다. 낮은 표기가격을 곧바로 3kg 가격으로 환산하지 않는다.
5. 약 30개의 중복 없는 확인된 판매처를 고정 패널로 선정한다. 매주 검색 노출 목록과 고정 패널 이력을 각각 유지한다.
6. 옵션 가격·배송비·추가요금·조건부 할인은 별도 확인값과 시각을 기록한다. 미확인 배송비는 null로 두고 배송 포함 비교에서 제외 사유를 표시한다.
7. 실제 중량이 확인된 표본으로 kg당 가격과 배송 포함 총액의 중앙값·범위를 제공한다. 전주·4주 비교는 동일 패널의 비교 가능한 표본 수를 함께 표시한다.
8. 호출 수·캐시·재시도 상한을 설정한다. 연결 확인은 소량 읽기 요청으로 수행하고 인증 실패 시 반복 호출하지 않는다. 장기 원응답 보관은 공급자 이용조건 확인 후 정한다.

## 7. 텔레그램: my_portal 참고 결과

확인 파일: `../my_portal/backend/telegram_notify.py`, `backend/briefing_scheduler.py`.

재사용할 방식은 서버 전용 발송 함수, `TELEGRAM_TOKEN`/`TELEGRAM_CHAT_ID` 구성, 15초 제한, 미설정 시 비활성, KST 예약과 부팅 시 무조건 재발송하지 않는 원칙이다. Python 코드를 그대로 가져오지 않고 프로젝트의 TypeScript 서비스로 구현한다.

여기에 발송 이력과 소유권 검사를 추가한다. 기존 my_portal의 단일 채팅방으로 모든 사용자 브리핑을 보내는 순회 구조는 이 프로젝트의 기본값으로 삼지 않는다. 초기에는 지정 소유자의 수신 설정만 사용한다.

- 봇 토큰과 채팅 ID는 별개 설정이며 실제 활성화 시 사용자가 제공한다. 지금은 mock/dry-run으로 준비한다. 앱 보고서 생성은 텔레그램 설정 없이도 가능하게 한다.
- 발송 전 `(briefingVersion, channel, recipient)` 고유 키를 점유한다. 결과는 SENT/FAILED/UNKNOWN/SKIPPED로 구분한다.
- HTTP 성공뿐 아니라 응답 `ok`와 메시지 ID를 검사한다. 429는 `retry_after`를 반영하며 횟수 상한을 둔다. 전송 여부가 모호한 타임아웃은 UNKNOWN으로 남겨 맹목적으로 재전송하지 않는다.
- 오류 로그에 토큰이 들어 있는 URL이나 요청 헤더를 기록하지 않는다. 전문 대신 짧은 요약·행동 3개·앱 링크를 보낸다.
- 초기 구현은 실제 발송과 예약 모두 OFF. 미설정을 성공 발송으로 기록하지 않는다.

응답·발송 계약 확인: [Telegram Bot API](https://core.telegram.org/bots/api#sendmessage).

## 10. 협업·비용 관리

### 이 프로젝트에 적용할 우선 설계

`NAS 주간 작업 큐 → 로그인된 Mac의 Codex 워커 → 검증된 보고서 초안 반환 → NAS 저장·텔레그램`

1. NAS가 가격 집계·출처·누락 상태를 포함한 불변 입력 스냅샷과 작업 ID를 만든다.
2. Mac 워커가 전용 인증으로 자기 작업을 가져와 lease를 점유한다. 현재 사용자의 대화 세션을 임의로 조작하지 않고 독립 `codex exec` 실행을 사용한다.
3. Codex에는 필요한 집계·근거만 제공하고 JSON Schema 결과를 요청한다. 본문 작성이 목적이므로 운영 DB·배포·발송 권한을 주지 않는다.
4. 서버가 스키마·인용 source ID·입력 버전·수치 일치 여부를 검증한 뒤 DRAFT로 저장한다. 실제 발행과 알림은 기존 별도 흐름을 따른다.
5. 실행당 시간·출력 길이·재시도 상한을 두고 작업별 사용량을 기록한다. 로그인 만료·구독 한도 소진은 명시적 대기 상태로 처리하며 유료 API로 자동 전환하지 않는다.
6. Mac이 꺼졌거나 절전 중이면 작업을 대기시키고 지연 상태를 앱에서 보여준다. 월요일 10시 무인 실행을 위해 Mac 가용성 또는 상시 실행 호스트를 확정한다. 인증 파일을 NAS 이미지에 복사하는 방식은 기본 설계로 삼지 않는다.

MCP는 수동 대화에서 농가 데이터를 조회하거나 초안 저장 도구를 제공하는 보완 경로로 적합하다. MCP 서버 자체가 매주 AI를 깨우지는 않으므로 예약 실행 워커를 대체하지 않는다. 로컬 Ollama는 별도 선택지이며 한국어 농업 보고서의 출처 준수·요약 품질을 평가한 후 채택한다.

이 방식은 별도 AI API 과금 계정 없이 기존 구독 인증을 사용하는 방안이다. 클라우드 모델 이용과 구독 사용량 소모는 계속 발생한다. 네이버 상품검색·기상 등 데이터 API와 프로젝트 내부 통신은 여전히 필요하다.

다음 검증 작업: (1) fixture 입력으로 Codex 결과 계약 준비, (2) 전용 워커 큐·lease 설계, (3) 인증 만료/한도/오프라인 시나리오 테스트, (4) 소량 실제 생성 비교 후 운영 위치 확정. 이번 조사에서는 워커 설치·예약 활성화·실제 생성은 하지 않았다.

## 12. 구현 진행 기록 — Codex 워커 방식 착수

위 §11 조사 후 사용자가 개발을 승인하여 다음 첫 실행 경로를 구현했다. 앞부분의 ‘설계 준비’는 최초 작성 시점 기록이며 현재 상태는 이 절을 따른다.

- 리포트 화면의 **주간 브리핑** 탭: 품목·품종·산지 조건으로 초안 요청, 작업 상태·근거 집계·누락 정보·생성된 초안 확인.
- 사용자별 워커 토큰 발급·폐기: 서버에는 해시만 저장, 재발급 시 이전 토큰과 진행 중 lease 무효화.
- NAS 작업 큐: 입력 해시 중복 방지, 소유 사용자 격리, 한 번에 사용자당 작업 하나, 만료 lease 최대 세 번 자동 복구, 명시적 실패는 수동 재시도.
- 초안 저장: 입력 버전·근거 ID·스키마 검사, 완료 재전송 멱등 처리. 모델 문장의 숫자는 거부하며 수치는 서버 원자료 집계 표로 표시. 이것이 모든 자연어 사실의 자동 검증을 뜻하지는 않으므로 결과는 DRAFT다.
- 지난 완결 KST 주의 동일 조건별 원자료 수량 가중평균. 모든 거래를 집계하며 그룹이 너무 많으면 조건을 좁히도록 오류를 반환한다. 원문의 공개 평균 참고 시계열과 섞지 않는다.
- Mac 워커: 로그인된 Codex의 비대화형 실행, 단발 작업·시간 제한·사용량 기록. 설치와 실행은 [워커 안내](../briefing-worker-setup.md), 서버/워커 통신은 [계약](../briefing-worker-contract.md)을 따른다.

검증: 전체 48개 파일·346개 테스트 통과, 빌드·타입 검사 통과, lint 오류 없음(기존 경고 28개). 임시 DB에 전체 migration을 적용해 작업 큐·사용자 격리·완료 멱등성·토큰 폐기를 확인했고, 가상 입력을 실제 로그인된 Codex로 생성하는 연결 검증도 통과했다. 전용 지침 적용 후 해당 작은 fixture의 입력은 21,127 → 15,899 토큰으로 감소했다. 상세 조건은 워커 안내의 검증 기록을 따른다.

이번 구현의 범위 밖: 기존 Work 보고서 전문 가져오기·정정 이력, 전주·네 주 비교, 산지별 품종 선택 UI, 공식 네이버 검색과 고정 경쟁점 패널, 재배·기상·물류 출처 수집, 자동 예약·텔레그램. 후속 단계는 §8 순서로 이어간다. NAS 배포와 제한된 실자료 초안 연결 검증은 완료했으며, 상세 결과와 남은 운영 개선은 [배포 검증 기록](2026-09-14-briefing-deployment.md)에 기록했다.

## 13. 수집 확인·기간 비교 구현

`0d40fb1`에서 AI 없는 시세 분석 미리보기, 품목·법인·날짜별 로그 확인, 동일 조건 원자료의 전주 및 직전 네 주 가중평균 비교를 추가했다. 최소 표본·수집 기록 기준에 미달하면 등락률을 보류하고 이유를 표시한다. 이전 §12의 전주·네 주 비교 미구현 상태는 이 후속 기능으로 갱신한다. 공개 일평균 시계열과 Work 원문/정정 이력 이전은 계속 남아 있다. 상세 규칙·한계·운영 검증은 [기간 비교 기록](2026-09-14-briefing-comparison.md)을 따른다.

## 14. 산지별 품종 선택·시세 분포 보강

주간 브리핑의 산지·품종 입력을 지난 완결 주와 사용자 선택 법인에 맞춘 관측 목록으로 연결한다. 기존 시세 분포는 산지·법인까지 구분하고 극단 가격 후보·물량 비중·관측 일수를 추가한다. 원본이나 대표 가격에서 후보를 자동 삭제하지 않는다. 규칙과 남은 개발 순서는 [산지·품종 및 분포 기록](2026-09-14-origin-variety-distribution.md)을 따른다.
