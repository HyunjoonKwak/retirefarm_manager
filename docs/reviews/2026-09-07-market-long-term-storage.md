# 최근 1년 원본과 다년 가격 비교 — 운영 확인 및 구현 설계

2026-09-07 KST. 로드맵 4를 최우선으로 조정한다. 이 문서는 운영 확인과 구현 계약이며, 집계 저장·다년 조회 구현 완료 보고가 아니다.

## 오늘 확인한 사실

- 09:30 정기 수집 로그: 5개 법인 SUCCESS, 1개 EMPTY, 신규 합계 4,956건. 정기 수집 자체는 복구됐다.
- 초기 확인 당시 원본 166,761건, 보관 설정 365일·자동 정리 true. 수집 직전 배포 보고의 195,490건보다 줄어든 것은 기존 90일 정리 때문이다.
- 삭제 전 백업 `/volume1/code_work/retirefarm_manager/backups/backup_20260907_083221.db.gz`는 실제 존재하며 압축 해제본 SQLite integrity_check가 `ok`다. 원본 195,490건, KST 거래일 4월 24일~9월 5일이다.
- 6월 9일 KST 이전 백업 자료는 **33,685건**, 수량 합계 **1,010,338**, 거래 금액 합계 **13,895,451,500원**이다. `195,490 + 4,956 - 33,685 = 166,761`로 초기 운영 건수와 일치한다. 건수 일치는 중복키별 복구 검증을 대신하지 않는다.
- 따라서 삭제 자료가 복구 불가능하다는 판단은 맞지 않는다. 백업으로 복구할 수 있다. 라이브 DB에 백업을 통째로 덮어쓰면 오늘 신규 거래와 설정·사용자 변경을 잃으므로 금지한다.
- Claude가 별도 사용자 지시로 자동 정리를 false로 변경하고 2026-04-09~06-08 백필을 시작했다고 보고했다. root의 대조 조회는 `database is locked`로 끝났다. root는 운영 DB를 수정하지 않았다. 백필과 백업 복구를 동시에 실행하지 않는다.
- 백업에는 토마토 107,993건, 포도 78,981건, 방울토마토 8,516건이 있다. 삭제 기준 이전은 각각 28,801건·2,237건·2,647건이다. 현재 수집 품목 토마토·포도만 백필하면 과거 방울토마토 원본이 전부 복구된다고 단정할 수 없다. 백필 후 반드시 백업 중복키 차집합을 확인한다.
- 14:03~14:05 점검에서 ready HTTP 503, scheduler true / recovery false, P1008 DB 시간 초과를 확인했다. `/proc/locks`에서 해당 DB inode의 잠금 소유자는 Next 서버 PID 19215였다. 잠금 원인까지 확정한 것은 아니다. 운영 작업 담당 Claude에 전달했으며, 이 시점에는 백필 완료·서비스 정상화를 선언할 수 없다.
- Claude의 컨테이너 재시작 후 14:07 root가 ready·marketSchedulerReady·marketRecoveryReady 모두 true를 직접 재확인했다. 잠금 재발 방지와 백필 재개 검증은 별도로 남아 있다.

## 복구와 보호 순서

1. 운영 쓰기는 Claude의 백필 작업 한 곳에서 담당한다. 날짜별 성공·0건·부분·실패와 신규 수량을 기록한다. 현재 진행 중인 창을 완료하거나 안전한 일자 경계에서 일시 정지한 뒤 백업 대조를 수행한다.
2. SQLite 온라인 backup API 또는 `.backup`으로 현재 상태의 일관된 백업을 만든다. 라이브 DB 파일 단순 복사는 journal/WAL과 동시 쓰기를 고려한 일관성을 보장하지 않는다.
3. 삭제 전 백업을 읽기 전용으로 연결하고 기존 AuctionResult 9필드 중복키로 차집합을 계산한다. 날짜뿐 아니라 품목·품종·법인·가격·산지·규격·등급·수량을 모두 사용한다. 기존 id 충돌도 별도 확인한다.
4. 차집합만 짧은 트랜잭션으로 삽입한다. 신규 수집 자료·사용자 설정·저장 조건·백필 로그를 교체하지 않는다. 원본 건수/수량/금액 대조와 재실행 시 추가 0건을 검증한다.
5. 자동 정리는 집계 저장과 조회 검증 완료까지 끈 상태로 유지한다. 365일 설정만으로 다년 원본 백필을 보호할 수 없다. 집계 구현 후에만 정책에 따라 정리를 다시 켠다.

## 저장 구조 제안

원본은 최근 365일을 보관하고 그 이전은 정확한 가격 분포를 유지하는 일별 집계로 옮긴다. 최초에는 과거 원본도 보존한 채 집계 결과를 병행 검증한다.

`MarketDailyAggregate`의 차원은 KST 일자·품목 원문·품종 원문·등급 원문·규격 원문·산지 원문·법인 원문이다. 법인코드는 부가 출처 정보로 보존한다. 원본 중복키가 법인명을 사용하므로 법인코드가 다른 동일 거래를 새 거래로 세면 안 된다.

저장값:

- schemaVersion, 원본 건수, 유효 건수와 제외 건수
- 수량 합계, 가격×수량 합계, 최소/최대 가격
- kg 환산 가능 건수·총 kg·해당 거래 금액
- 가격별 수량 합계와 건수의 정확한 분포
- 원본 중복 식별 증거, 집계 생성 시각 및 검증 체크섬

단순 가격 히스토그램만으로는 과거 날짜 재수집 시 기존 거래를 식별할 수 없다. 같은 차원 안에서 **원본 auctionDate 타임스탬프·price·quantity**의 고유 튜플을 보존하는 압축 분포를 기준 표현으로 제안한다. 조회용 가격 히스토그램과 합계는 이 표현에서 만든다. 날짜 표시는 KST로 통일하되 기존 중복키의 실제 타임스탬프를 버리지 않는다. 메타데이터 보존이 필요한 원본은 별도 압축 증거 파일을 검토한다.

이는 완전한 거래 원문 상세를 제공하는 구조는 아니다. id·인증·임시 품목명 등을 생략하면 과거 상세 화면에서 거래 원문처럼 표시하지 않는다. 같은 원천 거래가 나중에 가격·수량을 바꿔 반환되는 문제는 현재 중복키로도 수정/신규를 구별할 수 없다. 임의 덮어쓰기 대신 원천 식별자 또는 검증된 전체 날짜 교체 정책을 후속 결정한다.

백업 195,490건의 위 일별 차원 그룹은 **33,077개**였다. 따라서 집계 행 수만 기준으로 약 5.9:1이지만 분포·중복 증거 저장 비용이 별도로 든다. 수십 MB 또는 5년 1.5GB를 확정 용량으로 약속하지 않는다. 실제 직렬화·압축·인덱스 포함 크기와 읽기 지연을 표본으로 측정한다. 이 백업에서만 일자 정규화로 충돌하는 중복키는 0건이었으며, 다른 연도까지 보장하지 않는다.

## 원본 정리의 트랜잭션 조건

- 날짜 단위로 원본과 기존 집계를 중복 제거해 합친다. 같은 날짜를 재수집한 원본이 있어도 중복 합산하지 않는다.
- 건수·수량·금액·kg 합계·분포를 검증하고 집계 upsert와 해당 원본 삭제를 같은 짧은 트랜잭션 안에서 수행한다. 실패하면 삭제도 롤백한다.
- 조회에서는 raw+archive 합집합의 동일 식별자를 한 번만 센다. 집계가 있다는 이유로 그 날짜의 나중 원본 전체를 무시해서도 안 된다.
- 자동 보관 정리와 관리자 명시 삭제는 다른 동작이다. 명시 삭제는 집계까지 같은 범위에서 삭제하여 조회에 다시 나타나지 않게 한다. 반복 조회 캐시도 무효화한다.
- 기존 자동 정리, cleanup POST, cleanup DELETE, 특정 날짜 DELETE 경로를 전부 점검한다. 하나만 교체하면 다른 경로에서 자료가 계속 사라진다.

## 조회 계약

- 다년 조회는 명시적 from/to와 일/월 간격을 사용한다. 현재 days 최대 730일이며, 이를 넘는 history 요청은 30일로 조용히 대체된다. 단순 5년 버튼 추가로 해결되지 않는다. 잘못된 범위는 400으로 반환한다.
- 원본과 집계 모두 품목·선택 품종·산지·등급·규격에 같은 필터를 적용한다. 산지 선택에 따른 품종 활성 상태와 규격 후보에도 과거 집계가 반영돼야 한다.
- 평균은 기간 전체 `Σ금액/Σ수량`, 중앙값·25~75% 구간은 합쳐진 가격 분포로 계산한다. 일별 평균이나 중앙값을 평균하지 않는다. kg 환산이 모호한 규격은 계속 제외한다.
- 기존 분석 API의 최근 20,000건 절단을 다년 통계에 그대로 적용하지 않는다. 완전한 집계 경로 또는 명확한 제한 오류를 제공한다.
- 응답에 requestedRange, observedRange, source(raw/aggregate/mixed), 통계 버전, 원본 상세 가능 여부, 날짜별 수집 상태를 포함한다.
- 수집 상태는 일자×법인×품목 범위의 최신 유효 로그로 판정한다. 성공/검증된 0건/부분/실패/미수집을 구분한다. 거래가 없다는 이유로 휴장으로 단정하지 않는다. 기존 로그로 완전성을 입증하지 못하면 unknown으로 표시한다.
- 연도 비교는 동일 조건·동일 달력 구간으로 겹쳐 보여 주고 윤일과 미수집 공백은 연결하지 않는다. 작년 대비 숫자는 비교 양쪽의 자료 범위와 표본 수를 함께 표시한다.

## 재개 가능한 다년 백필

기존 market-backfill.cjs는 62일 창·완료 저널·중복키를 제공하지만 다년 운영 큐는 아니다. 다음을 추가한다.

1. DB의 날짜×법인×품목 작업 상태, lease, 시도 횟수, 다음 시도 시각, 진행률, 일시 정지와 재개를 영속화한다.
2. 1회 최대 날짜 수/실행 시간/요청 수와 KST 야간 실행 창을 제한한다. 09:30 정기 수집 및 보충 작업과 쓰기 충돌을 피한다. 고정된 2.8시간 완료 예상은 사용하지 않고 관측 처리율로 갱신한다.
3. 저널에 complete가 있어도 DB 복구·삭제로 실제 자료가 사라졌을 수 있다. 아카이브 manifest 및 수집 증거와 대조한 경우에만 skip한다. EMPTY도 검증된 수집 증거가 있어야 완료다.
4. 2021~2025년 각 한 날짜의 API 응답은 해당 표본의 조회 가능성만 입증한다. 연속 5년 전체 지원을 가정하지 않는다. 연도별 완료/부분/0건/실패 비율과 최초 실제 자료일을 보고한다.
5. 365일 이전 백필을 먼저 검증된 집계로 옮길 수 있어야 원본 용량이 안정된다. 그 전까지 자동 정리를 꺼 둔다.

## 구현 완료 기준

- 같은 자료를 정리 전후 조회했을 때 모든 필터의 건수·가중평균·kg 단가·분위수·공백 상태 일치
- 재수집/동시 수집/재시작/검증 실패/명시 삭제/원본과 집계 중첩 통합 테스트
- 5년 표본에서 응답 시간과 메모리 측정, 원본 상세와 집계 상세를 구별하는 UI 확인
- 복구 백업 유지, 실제 마이그레이션·배포·ready 상태 확인 후 자동 정리 재활성화

별도 작업: 원천 QTY 누락 시 1로 대체된 기존 행은 DB만으로 구별할 수 없다. 향후 수량 출처 필드를 추가하고 과거 가중치의 한계를 표시한다. 품종·산지 별칭 승인은 이 저장 변경과 별도로 수행하며 원문을 덮어쓰지 않는다.
