## 결론

현재 관심 품목, 품종·산지·포장 단위 필터, 추이 차트, 일별 거래 상세, 수동·예약 수집이 구현되어 있다. 다음 목표는 **내가 재배하는 품종과 출하 규격의 가격을 믿고 비교하고, 예상 수취액을 판단하는 도구**다. 수집 정확성 → 비교 기준 통일 → 개인화·알림 → 출하 수익 → 장기·다시장 비교 순서를 권한다.

### 격리 재현 결과

실제 서비스 TypeScript를 메모리에서 CommonJS로 변환하고 Prisma·fetch·logger를 대체해 검증했다. 테스트용 환경값만 사용했으며 운영 데이터에는 접근하지 않았다.

1. HTML 오류 본문 → `{list_total_count: 0, items: []}`.
2. 모든 네트워크 요청 실패 → DB 모형의 로그는 `FAILED`, 서비스 반환값은 `noAuction: true`.
3. 총 20건을 알리는 첫 페이지 모형에 거래 1건을 넣고 2페이지 실패 → 1건 저장, 로그 `SUCCESS`. 첫 페이지의 비정상 건수도 검출되지 않는다.
4. DB 일괄·개별 저장 모두 `disk full` 오류 → 중복 1건, 로그 `SUCCESS`.
5. 전날 5kg 1상자×10,000원 + 10kg 10상자×20,000원, 다음날 5kg 10상자 + 10kg 1상자로 구성만 변경 → 모든 거래가 2,000원/kg인데 관심 품목 가격은 10,909원/5kg, 등락률 약 **-42.86%**. 이는 운영 시세가 아닌 결함 재현용 예시다.

기존 서비스 테스트는 XML 정상 파싱·날짜·kg 추출 위주다. 수정 시 위 실패 경로, 부분 수집 후 재실행, 혼합 단위, 동일 규격 비교를 회귀 테스트로 추가하는 것이 효과적이다. 이번 읽기 중심 검토에서는 전체 테스트와 빌드를 반복하지 않았다.

## 다음 개발 묶음과 완료 기준

### 추가 요청: 품종별 가격 분포 분석

단위 통일만으로 해결되지 않는 품종·등급별 가격 차이를 가공하는 방법을 [품종별 가격 분석 설계](2026-09-06-variety-price-analysis.md)에 추가했다. Codex는 통계·정규화·검증, Claude는 비교 화면·오해 방지를 검토했다.

2번 ‘비교 규격·통계 통일’의 완료 기준에 **품종별 분리 계열, 물량 가중 중앙값(P50), 주요 거래 구간(P25~P75), 거래량·표본 수·품질 상태**를 포함한다. 여러 품종을 선택해도 하나의 평균으로 합치지 않는다. 품종 비교표 → 분포 확인 → 원천 거래 → 내 출하 조건 저장으로 이어지는 분석 도구를 만든다. 품종 별칭 사전, 이상 가격 진단, 거래 구성 변화 설명은 후속으로 붙인다.

가격이 높거나 낮다는 이유만으로 거래를 삭제하지 않고, 품종 자체의 차이와 등급·규격·표본 편중을 구분한다. 전체 평균 상승과 개별 품종 가격 상승을 분리하며, 표본이 부족하면 다른 품종을 자동 혼합해 대표값을 만들지 않는다. 자세한 계산식·희소 표본 규칙·API 계약·인수 테스트는 연결 문서를 따른다.

품종 비교표의 첫 구현에는 **산지 연동 품종 선택**도 포함한다. 산지·기간에 거래가 확인된 품종을 강조하고 기본 목록에 표시하며, 전체 보기에서는 기간/규격 불일치와 기록 미확인을 구분한다. 기존 선택은 무단 해제하지 않고 결과 없는 이유와 조건 해제 동작을 제공한다. 경매 기록만으로 ‘그 지역에서 생산하지 않는다’거나 ‘현재 출하 중’이라고 확정하지 않는다. 선택지 API·산지 사전·응답 순서·접근성 규칙은 품종별 분석 설계서에 명시했다.

### Claude 화면 검토를 합친 사항

- **관심 품목과 비교 조건을 상단에 배치:** 현재 `MarketPriceManager.tsx:680,692,746`은 차트 다음에 필터, 페이지 하단에 관심 품목을 배치한다. 모바일에서 자주 보는 품목과 가격의 기준을 먼저 확인하도록 관심 품목 → 비교 조건 → 요약 → 차트 → 상세 순서를 권한다. 이는 UI 코드 순서에 근거한 검토로, 실제 모바일 사용성 실험은 하지 않았다.
- **기기 간 설정 동기화:** 품목 목록·필터·프리셋이 `MarketPriceManager.tsx:42` 이후 localStorage에 저장되고 관심 품목만 DB에 있다. 로그인 사용자 설정으로 동기화하고, 빈 차트에는 미수집·해당 규격 거래 없음·수집 오류를 구분해 다음 행동을 제공한다.
- **재배 작물과 시세 품목을 명시적으로 연결:** 작물명이 자유 입력이므로 이름을 강제로 바꾸기보다 원래 작물명은 보존하고 표준 시세 품목·품종 연결 필드를 둔다. 수확 예정일 부근의 계절 비교는 장기 자료 확보 이후 제공한다.
- **실제 판매단가 비교 기반 마련:** 현재 판매 거래에는 작물 연결은 있으나 수량·단위 입력이 없다. 선택적으로 판매량·규격·판로·공제 비용을 저장해야 시장 시세 대비 성과를 비교할 수 있다. 직거래와 경매는 판매 단계와 비용 조건을 함께 표시한다.

Claude가 제안한 거래량 최다 단위는 초기 추천에 활용하되 사용자가 확인한 비교 규격을 저장하는 방식으로 조정한다. 매일 최다 단위를 자동 변경하면 일별 비교가 다시 흔들린다. 또한 기존 `SUCCESS` 로그만으로 알림을 보내는 방식은 위 부분 수집 결함 수정 이후에만 적용한다. 3년 계절 자료는 현재 보관 정책만으로 확보되지 않으므로 즉시 가능한 기능으로 분류하지 않았다.

### 이미 있는 구조를 활용할 곳

- `ProductWatchlist.targetPrice`와 API 저장 필드는 있지만, 현재 알림 체크 API에는 가격 조건 평가가 없다. 저장 필드만으로 기능이 완성된 것은 아니다. 목표 단위·비교 조건·상향/하향·중복 억제를 함께 설계한다.
- 레거시 `PriceWatchlist`/`PriceAlert`/`MarketPriceCache`와 현재 가락시장 모델이 공존한다. `/api/market/prices`는 고정 품목 목록과 캐시 읽기를 사용한다. 새 기능 전에 실제 소비 경로를 확인하고 현재 모델로 통합할지 결정한다. 이 경로가 가짜 시세를 생성한다고 판단한 것은 아니다.
- 동일 필드 조합을 중복 거래로 제거하는 현재 키는 제공기관 거래 식별자 의미를 확인해야 한다. 내용이 같은 서로 다른 거래가 가능한지는 원천 명세·표본 대조가 필요하므로 확정 결함으로 세지 않았다.

## 데이터 공급원 확장 판단

전국 확대에는 [한국농수산식품유통공사 전국 공영도매시장 실시간 경매정보](https://www.data.go.kr/data/15141808/openapi.do)를 후보로 권한다. 공식 안내에는 시장·법인·단위·포장·등급·산지 등의 표준코드가 연결되어 있어, 문자열 중심인 현재 모델을 정규화하는 데 도움이 된다. 실제 연동 전 승인·호출량·필드 의미를 확인하고, 가락시장 표본과 같은 날짜·규격의 건수·금액을 대조해야 한다.

단, 2025-11-20 [공식 API 변경 공지](https://www.data.go.kr/bbs/ntc/selectNotice.do?originId=NOTICE_0000000004410)는 새 `katRealTime2/trades2`와 낙찰일시 기준 최대 1개월 조회를 안내한다. 실시간 API를 연결한다고 수년치 과거 자료가 자동 확보되지는 않는다. 장기 분석용 정산·과거 자료의 제공 범위를 별도 확인해야 한다. 이 변경 공지는 현재 가락시장 `data12` API 폐지를 의미하지 않는다.

[KAMIS Open API](https://www.kamis.or.kr/customer/reference/openapi_list.do)는 일별 품목별 도·소매 가격을 제공하므로 보조 비교 지표 후보다. 경매 낙찰가·도매 조사 가격·소매 가격은 출처와 거래 단계를 표시해 별도 계열로 제공하는 것이 적절하다. KAMIS 상세 페이지 본문은 도구 접근이 실패하여 공식 검색 결과의 제공 기능까지만 확인했다.
