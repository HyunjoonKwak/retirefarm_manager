# 시세 자동 보충·운영 감시

## 구현

- 최근 7일의 예약분을 KST 기준으로 점검한다. 설정 생성 이전, 수집 요일 밖, 예정 시각에서 60분이 지나지 않은 예약은 제외한다. `collectDaysAgo`를 적용한 실제 수집 대상 날짜를 사용한다.
- 부팅 5초 후와 매 15분마다 확인한다. 동일 품목 조건에서 모든 대상 법인의 최신 로그가 SUCCESS/EMPTY인 날짜는 API를 다시 호출하지 않는다. 최초 점검에 완료 자료가 없으면 보충 작업을 만든다.
- 보충 작업은 DB에 저장하고 한 번의 점검에서 최대 3개 날짜를 실행한다. 날짜·설정·품목/법인 조건별 최대 3회, 실패 후 최소 1시간 간격이다. API 요청 자체의 제한 재시도는 기존 수집기의 정책을 따른다.
- DB 임대 토큰과 30초 갱신으로 중단된 작업을 재개한다. 임대 시간은 5분이며 실행 중에는 갱신된다. 설정을 끄거나 조건이 바뀌어 실제 API를 호출하지 않은 취소는 시도 횟수를 소모하지 않는다. 같은 조건을 다시 켜면 취소 작업도 재개 가능하다.
- 3회 실패/부분 수집 또는 마지막 시도 중 프로세스 중단은 앱 알림으로 한 번 알려준다. 알림과 완료 표시는 같은 DB 트랜잭션으로 저장한다. 이메일·메신저 전송은 추가하지 않았다.
- 부팅 DB 오류나 일부 예약 등록 실패는 다음 점검에서 재등록을 시도한다. 변경 없는 정상 예약은 유지하여 전체 예약을 반복 해제하지 않는다. 백업 초기화 실패도 시세 초기화를 가로막지 않게 분리했다.
- 기존 `/api/health`는 웹 서버 생존 상태와 시세 등록 여부를 계속 제공한다. 새 `/api/health/ready`는 시세 등록과 자동 점검기의 실제 생존 여부를 검사해 200/503을 반환한다. Docker healthcheck도 이 경로를 사용한다. 정상적인 장기 보충 중에는 진행 신호를 갱신하고, 35분 이상 신호가 끊기면 준비 실패로 표시한다. Docker의 unhealthy 표시는 자동 재시작 기능 자체가 아니다.
- 데이터 수집 화면에 자동 보충 상태, 재시도 횟수·다음 시각·실패 안내를 추가했다. 화면이 보일 때만 60초 주기로 조회하며, 조회 실패를 정상으로 표시하지 않는다. 완료 기록이 없다는 이유만으로 모든 날짜가 수집됐다고 단정하지 않는다.

## 변경과 검증

- 새 migration `20260907000000_market_recovery`: MarketRecoveryJob 테이블, 설정/조건/날짜 고유키, 상태 인덱스, 설정 삭제 시 cascade. 기존 거래 자료를 바꾸거나 삭제하지 않는다.
- 전체 테스트 230건 통과. 임시 SQLite에 모든 migration 적용 후 실제 Prisma로 완료 로그 건너뛰기, 재시도 간격/상한, 알림 한 번 생성, 만료 임대 재개, 마지막 시도 중단 처리, 사용자 격리, 한 점검 3건 상한을 검증했다.
- 날짜·유예 시간·요일·조회 범위·품목 조건은 순수 함수 테스트로 확인했다. UI 8건과 초기화·준비 상태 테스트도 포함한다.
- Claude는 상태 UI와 교차 검토를 맡았고, Codex는 실행기·DB·테스트·배포를 담당했다. 취소 후 재개, 정상 예약 유지, 장기 실행 준비 판정 문제를 교차 검토 후 보완했다.

## 남은 사항과 사용자가 확인할 것

추가 필수 설정은 없다. 기존 자동 수집을 켠 설정에 자동 보충이 적용된다. 사용자는 품목·법인·수집 시각이 맞는지 확인하고, 3회 실패 알림이 나타나면 데이터 수집 화면에서 로그를 확인하면 된다. 7일 예약 범위를 넘는 오래된 누락은 기존 수동 복구 도구로 처리한다.

9월 7일 09:30 KST 정기 실행 결과는 해당 시각 이후 확인할 사항이다. 실제 미래 실행까지 미리 검증했다고 주장하지 않는다. 품종/산지 표준화, 비교 규격 저장, 장기 집계, 목표가 알림은 다음 개발 묶음으로 남아 있다.
